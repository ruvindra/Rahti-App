1. Describe reasons why so many (most?) companies are using cloud based email and calendar services

Companies increasingly favor cloud-based email over traditional on-premises servers for several practical reasons.

  • Convenience is the most important reason. As long as there's an internet connection and a device, employees can access their messages from anywhere, rather than being tied to office infrastructure.
  • Cost is a major factor too. An in-house server looks cheap at first glance, but the real cost adds up quickly such as the server hardware, the operating system and email platform licenses, the physical rack, plus ongoing electricity, cooling, and IT staff to maintain it all. Cloud providers absorb these costs and spread them across many customers.
  • Security tends to be stronger with cloud providers. Large providers treat security as a top priority and typically have more resources and expertise than an individual company could dedicate to protecting an in-house server. Cloud services also scale automatically as a company grows, so businesses don't need to worry about expanding their own infrastructure.
  • Scalability is another advantage. As a company grows, the provider handles the scaling of infrastructure, freeing the internal team to focus on their actual work rather than expanding server capacity.
  • Disaster recovery is far easier with cloud email. If an on-premises server is infected or fails, recovering that data can be difficult or even impossible. Cloud platforms build in redundancy, so messages, contacts, and other data can typically be restored quickly.

Source: Microsoft — 5 ways cloud email is a must-have for your business

2. What would a mid-size company store to the Amazon Glacier? What not? Why? What other large cloud backup or mass storage providers are there?

Glacier fits data that is rarely accessed but needs to be kept for a long time. Good candidates include regulatory compliance archives, such as financial, tax, and legal records; disaster recovery backups, such as old server and database backups; and historical data, such as archived emails, old security footage, and completed project files.

What doesn't belong there are active files that employees access regularly, high-traffic web assets such as images or scripts used by a live website, or data that will be deleted soon. Glacier storage classes are designed for long-term storage and can have minimum storage-duration charges.

The main trade-off is low storage cost versus slower and potentially more expensive retrieval. Some Glacier storage classes can be extremely inexpensive for long-term archiving, but retrieving large amounts of data can take longer and may incur retrieval and data-transfer charges. Therefore, Glacier is ideal for data that can be stored and rarely accessed, rather than data that is actively used.

Other cloud backup and mass-storage providers include Microsoft Azure Blob Storage, Google Cloud Storage, Backblaze B2, Wasabi, iDrive e2, Hetzner Storage Box, and Scaleway. Several of these services can also be used with rclone, making them suitable for automated backups.

Sources: FileCloud — System admin guide to cloud storage, r/DataHoarder discussion

3. Select and describe 2-3 well-known Amazon S3 data leak incidents. What went wrong? List some automated S3 bucket search engines and attack tools (don't try the tools, illegal!)

Deep Root Analytics (2017) — A political data firm left voter profiling data on a completely open S3 server, exposing personal information and predictive voting behavior data for roughly 198 million Americans. The bucket had no authentication at all, meaning anyone who found the URL could access it.

Accenture (2017) — One of the more damaging leaks: at least four S3 buckets were set to public, exposing master access keys for Accenture's AWS account, 40,000 plaintext customer passwords, decryption keys, certificates, and proprietary source code. This wasn't just a data exposure — it handed attackers the credentials needed to potentially access deeper systems.

Verizon (2017, twice) — First, a Verizon partner exposed 6 million customer call-log records on a public S3 bucket. Months later, a Verizon engineer set up a separate, unauthorized S3 account containing internal technical data, including server architecture details and login credentials.

In all these cases, boiled down to the same root cause: S3 buckets were misconfigured to allow public access, often with no authentication required at all. This wasn't a flaw in AWS's infrastructure. It was human error in setting bucket permissions, frequently made worse by third-party vendors or contractors who had access to the data but didn't follow proper security practices.

Automated S3 bucket search/discovery tools:

  • GrayhatWarfare — a searchable index of publicly exposed S3 buckets
  • S3Scanner — checks for open/misconfigured buckets by name
  • Bucket Stream — monitors certificate transparency logs to find bucket names as they appear
  • AWSBucketDump — enumerates and dumps content from open buckets given a wordlist
  • Slurp — searches for buckets tied to a domain or keyword across providers

Source: Bitdefender — Worst Amazon S3 breaches

4. Describe reasons, why many IoT devices (internet connected home appliances, Smart-TVs and such) are using Google's 8.8.8.8 or some other public DNS resolvers?

Many IoT devices, such as smart TVs, connected appliances, and streaming boxes, hardcode a public resolver like 8.8.8.8 instead of relying on the local network's DNS for a few practical reasons.

  • Reliability and consistency: manufacturers want their devices to work the same way regardless of what router or ISP a customer has. A public resolver like Google's is highly available and consistent worldwide, removing dependence on potentially unreliable or poorly configured home routers and ISP DNS servers.
  • Simplicity for the manufacturer: standardizing on a single, well known resolver across an entire product fleet means the vendor doesn't need to account for the huge variety of DNS setups their devices might encounter. It's one less variable to support or debug.
  • Speed: Google's DNS uses a large anycast network, so queries are typically resolved quickly from a nearby server, which is useful for devices needing fast, reliable connections to streaming services or update servers.
  • Bypassing weak or restrictive local DNS: some ISPs hijack unresolved domains to show ads, or have DNS infrastructure that's slow or unstable. By hardcoding a public resolver, device makers avoid those quirks and ensure predictable behavior.
  • Avoiding local network filtering and parental controls: this can be a downside for the user, since a device hardcoded to 8.8.8.8 may bypass DNS level content filters or parental controls set up on the home router, as it doesn't use the local resolver at all.

The trade off is that this reduces the household's control over the device's DNS behavior and sends its query data to a third party (Google) rather than keeping it local, which is a privacy and control concern some users raise about IoT devices in general.

Source: CaptainDNS — Why 8.8.8.8?
